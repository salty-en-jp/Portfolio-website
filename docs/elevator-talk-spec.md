# Elevator Talk（仮）仕様書 v0.1

## 目的

**「場面とセリフの型があれば、とっさに英語を話し切れるか」を確かめる。**

帰国後に「なんか英語で言ってよ」と言われて困った経験、劇や歌ならセリフが出てきた経験、
宝探しで「知らないと理不尽ゲーになる」と分かった経験から立てた仮説を、英語サークル企画の
「エレベータートーク」と「違和感チェック」を土台に検証する。

## 想定ユーザー

- 英語で会話したいが、とっさに言葉が出ない初級〜中級者
- サークルのメンバー、ポートフォリオを見た採用担当者（その場で試せること）

## 画面の流れ

```
テーマ表示 → セリフの型を3つ表示 → 30秒タイマー（1F→5Fのエレベーター）
  → 話す（マイク）または打つ（キーボード／スマホ）
  → 文字起こし結果を確認・修正
  → フィードバック（よかったところ／改善ポイント）
  → 改善ポイントを「自分の違和感チェック」に保存
```

## 機能と優先度

締め切り 2026-11-02 までに **Must** を必ず公開する。Should 以降は間に合った分だけ入れる。

| 優先度 | 機能 | メモ |
|---|---|---|
| Must | テーマとセリフの型の表示（最初は5テーマ） | 型は段階的に減らせる構造にしておく |
| Must | 30秒タイマーとエレベーターのアニメーション | 1F→5F |
| Must | キーボード／スマホ入力 | マイクが使えない環境の標準経路 |
| Must | マイク入力＋文字起こし | ブラウザの音声認識が使える環境のみ。使えなければ入力欄に切り替える |
| Must | 自己チェック（話し切れた／途中で止まった） | AIなしでも成り立つ最低限の振り返り |
| Should | AIフィードバック（よかったところ／改善ポイント） | 下の「AIの使い方」を参照 |
| Should | 違和感チェック（通常問題） | 不自然な英文→自然な表現を選ぶ。最初は10問を手作り |
| Could | 違和感チェック（自分のまちがい問題） | AIフィードバックの改善ポイントから自動で出題 |
| Won't（今回） | アカウント、ランキング、発音の採点 | |

## AIの使い方

### 返してもらう形

AIには自由な文章ではなく、決まった形（JSON）で返させる。こうすると画面に並べやすく、
違和感チェックの問題にもそのまま使える。

```json
{
  "good_points": ["理由まで言えている", "My favorite food is ... の型を使えている"],
  "improvements": [
    {
      "original": "I like it because it is very delicious.",
      "natural": "I love it because it's so tasty.",
      "reason": "delicious に very はあまり付けない"
    }
  ]
}
```

### 「自分のまちがい問題」の作り方

1. `improvements` の1件ずつを、ブラウザ（localStorage）に保存する
2. 違和感チェックで、`original` を見せて「どこが不自然？」と聞く
3. 選択肢は `natural`（正解）と、通常問題から借りた不正解で作る
4. 正解したら出題頻度を下げ、間違えたら残す

### APIキーの扱い（要決定）

GitHub Pages は静的サイトなので、ページの中にAPIキーを書くと誰でも盗めてしまう。

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 中継サーバー | Cloudflare Workers などにキーを置き、ページはそこを呼ぶ | 誰でもそのまま試せる | アカウント作成と設定が必要。使われすぎ対策（回数制限）が要る |
| B. 自分のキーを入力 | 使う人が自分のAPIキーを入れる | サーバー不要 | 採用担当者は試せない |
| C. AIなし | 型の使用チェックなど、決まったルールで判定 | 費用ゼロ・確実 | 指摘の質は低い |

公開版はAかCに倒すのが現実的。料金や無料枠は、使う前に各サービスの公式ページで確認する。

## 注意点

- AIの添削は間違えることがある。「自然な表現」は自分の英語感覚でも確認する前提にする
- 話した内容は外部のAIサービスに送られる。画面にそのことを明記する
- 文字起こしはブラウザによって精度や対応が違う（特にiPhoneのSafari）
